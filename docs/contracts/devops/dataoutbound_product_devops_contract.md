## Open review comments

- conn-imp-13 / node imp-standard-standard_sftp-11: the draft invents the name 'customer sftp destination' / module 'customer_sftp_destination'. The baseline infra spec (§3.1) fixes this component as 'customer SFTP server' with terraform resource 'customer_sftp_server'. Use those names verbatim so both generated sides agree.
- conn-imp-14 / node imp-aws-aws_s3_bucket-12: the draft invents 'customer s3 bucket destination' / module 'customer_s3_destination'. The baseline fixes the component as 'customer bucket' with terraform resource 'customer_bucket_s3' (also referenced by IAM Sid S3CustomerBucketPush). Rename to match or every generated module will diverge from the Terraform module.
- conn-imp-15: field 'sas_token_or_identity' contradicts the baselines, which mandate Microsoft Entra ID / SSM Parameter Store credentials and explicitly avoid shared-key/SAS access; the draft should express this as an SSM SecureString credential parameter, not a SAS-token union type, or the two workers will build incompatible auth paths.
- conn-imp-3: description introduces a 'mediator Lambda' that is not a node in the edge set or the architecture diagram; the infra spec resolves the trigger Lambda as a supporting resource inside the scheduler component. Reword to reference the scheduler's built-in trigger mechanism, not a new intermediary component.
- conn-imp-7: 'watermark_query' is a value-level artifact (exact SQL owned by one side) and over-specifies; keep only the structural need (config row + watermark state read) and leave the query text to RSVP.
